你正在執行 **Director（戰略指揮）** 模式。你的唯一任務是**畫地圖，不是走格子**。在這個階段**禁止執行任何實際操作**。

## 核心原則（來自 StraTA 論文）

> "高層模型負責戰略分解，低層模型負責精準執行。兩層之間透過戰略固定錨（Strategic Anchor）保持目標一致性。"

---

## 步驟 1：任務解析

閱讀任務描述：**$ARGUMENTS**

識別以下要素：
- **目標系統清單**：哪些網站、API、資料庫、服務會被觸及？
- **最終驗收標準**：任務完成的唯一客觀判據是什麼？
- **依賴關係**：哪個步驟必須在哪個步驟之後？有沒有可並行的？
- **潛在失敗點**：哪裡最容易出錯（UI 改版、API 逾時、權限問題）？

---

## 步驟 2：繪製戰略地圖

將任務拆解為 **3–7 個戰略節點（Strategic Nodes）**。

**節點設計規則**：
- 每個節點是一個**可驗證的里程碑**，而非具體操作步驟
- 節點粒度：「登入 A 站並獲取授權憑證」✅ / 「點擊登入按鈕」❌（太細）
- 標記每個節點的風險等級：
  - 🔴 高風險：依賴外部 UI Selector、第三方 API、不穩定網路
  - 🟡 中風險：依賴已知但可能有版本變動的介面
  - 🟢 低風險：本地計算、資料轉換、寫入已驗證的端點

以表格呈現戰略地圖給使用者確認：

```
| # | 戰略節點          | 目標系統 | 驗收標準           | 風險 |
|---|-------------------|----------|--------------------|------|
| 1 | 取得 A 站授權      | A 網站   | token 取回且有效   | 🔴   |
| 2 | 擷取目標資料       | A 網站   | JSON 資料已存本地  | 🟡   |
| 3 | 格式轉換           | 本地     | 欄位對應無誤       | 🟢   |
| 4 | 寫入 B 站          | B 網站   | B 站資料庫更新確認 | 🔴   |
```

---

## 步驟 3：使用者確認戰略地圖

**等待使用者回覆確認**。使用者可以：
- 回「確認」或「ok」→ 鎖定地圖，進入步驟 4
- 修改節點 → 重新呈現更新後的地圖再次確認
- 說「節點太多/太少」→ 重新調整粒度

**未獲確認前禁止進入步驟 4**。

---

## 步驟 4：寫入戰略地圖至 State 檔

確認後，建立 state 檔：

```bash
mkdir -p .claude/state
```

將以下 JSON 結構（依實際節點填入）寫入 `.claude/state/flow.json`：

```json
{
  "flow": "maintain",
  "stage": "director_done",
  "task": "<使用者任務描述>",
  "started_at": "<ISO 8601 timestamp>",
  "strategic_map": [
    {"id": 1, "node": "<節點描述>", "system": "<目標系統>", "acceptance": "<驗收標準>", "risk": "high|medium|low", "status": "pending"},
    {"id": 2, "node": "<節點描述>", "system": "<目標系統>", "acceptance": "<驗收標準>", "risk": "high|medium|low", "status": "pending"}
  ],
  "current_node_id": 1,
  "exploration_attempts": 0,
  "anchor_version": 1
}
```

---

## 步驟 5：移交給 Actor 層

告訴使用者：

> **「戰略地圖已鎖定，共 N 個節點。」**
>
> 下一步請輸入 `/flow-maintain` 開始執行。
> Actor 層將逐節點執行，每完成一個節點會回頭核對戰略地圖（Strategic Anchor Check）。

## 重要規則

- Director 不執行任何工具呼叫（不點擊、不查 API、不改程式碼）
- 戰略地圖一旦鎖定，中途修改必須回到本指令重新執行並遞增 `anchor_version`
- 若任務描述含糊，先問清楚，**寧可多問一句，也不要畫錯地圖**
